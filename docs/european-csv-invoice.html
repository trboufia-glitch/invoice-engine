Your European invoice CSV breaks silently

A file containing 1.234,56 and semicolon delimiters does not throw an error in most validators. It produces wrong numbers, quietly. That is worse than a crash.

The three formats that collide

Written asMeansNaive parser produces
1,234.56one thousand two hundred1234.56 ✓
1.234,56one thousand two hundred1234.56 or 123456 ✗
1 234,56one thousand two hundred1234.56 or 123456 ✗
1'234.50one thousand two hundred (CH)123450 or NaN ✗
(250.00)minus 250 (accounting)+250 ✗

The rule is simple and every correct implementation follows it: whichever of . or , appears last is the decimal point. Everything before it is a thousands separator.

The delimiter problem is worse

In every locale that uses a comma decimal separator, the field delimiter is a semicolon. A parser that splits on commas turns this:

// the actual file (German export)
Invoice No;Net;MwSt;Gesamt
R-77;1.000,00;190,00;1.190,00

// what a comma-splitting parser sees
one field: "Invoice No;Net;MwSt;Gesamt"
          "R-77;1.000,00;190,00;1.190,00"

Nothing throws. The row count looks plausible. You simply get structurally valid garbage — and it is indistinguishable from a real record until someone queries the invoice.

This is the gap, and it is checkable

The established invoice validators market totals and VAT. Searching their documentation for 1.234,56, semicolon, delimiter, locale and European returns nothing. They validate arithmetic; they do not validate the format the arithmetic arrived in.

So a file can pass their check and still be wrong by a factor of a thousand.

What actually catches it

  • Detect the delimiter per file — count , ; tab and | across the header, use the winner
  • Parse numbers on the last separator, not the first
  • Treat (250.00) as negative
  • Treat an empty cell as missing, never as 0
  • Reject 2026-02-31 instead of rolling it into March

That is the whole list, and it is roughly four hundred lines of code with no dependencies and no model in the loop.

It is not magic, and it is not an LLM

There is no model here. That is deliberate: a model can invent an invoice number, and a fabricated figure inside a ledger is worse than no answer at all. This is regex and arithmetic, which means it is free to run, takes about a millisecond for a five-row file, and returns byte-identical output for identical input.

The repository is public, including the ten bugs found while building it. The first one was exactly this: the CSV splitter was hardcoded to commas while the detector chose semicolons — so every European export collapsed into a single column.
